# Validity Frontmatter, version 1.0

An open vocabulary for declaring, inside a plain text document, that the document has a lifetime and
that it may have been replaced.

| | |
|---|---|
| **Version** | 1.0.0 |
| **Status** | Draft. Stable enough to implement; breaking changes require a major version. |
| **Date** | 2026-08-19 |
| **License** | This specification and any reference code in it are released under the MIT license. |
| **Reference implementation** | [TypeScript, MIT, zero dependencies, Level 3](../reference/typescript/) — one file, runs in a browser, in Node, and in an Obsidian plugin on desktop and mobile alike. |
| **Origin implementation** | [RE-call](https://github.com/GiulioDER/RE-call), Apache-2.0. The specification is deliberately licensed more permissively, so that adopting the vocabulary carries no obligation to adopt the engine. |

Anyone may implement this specification, in any language, for any purpose, without permission and
without attribution. It describes three YAML keys and the rules for interpreting them. It describes
no storage engine, no ranking function and no product.

---

## 1. Why this exists

A collection of notes that is kept over time is a record of changing beliefs, not a set of facts.
Decisions get reversed. Limits get raised. Experiments get falsified. The note recording the old
belief is not deleted, because deleting it would destroy the history, so both the old note and its
correction sit in the corpus together.

Similarity search cannot tell them apart. Worse, it usually prefers the wrong one, because the
superseded note is often the more focused, more confidently worded document. A measured example
from the reference implementation's own demo corpus:

```text
query: how many requests per second can a client make?

  cos=0.784  rate_limits_v2.md   # API rate limits (revised)
  cos=0.806  rate_limits_v1.md   # API rate limits ... limited to 100
```

The stale note scores **higher**. Every retrieval system that ranks on distance alone serves it,
and every language model downstream of one narrates it as current.

No amount of ranking work fixes this, because the ranker has no notion of validity to rank on. The
information that `rate_limits_v2.md` replaced `rate_limits_v1.md` is not in the text, not in the
embedding and not in the filesystem. Somebody has to write it down.

This specification is the smallest way to write it down.

## 2. Scope

**In scope.** Three document properties, the rules for resolving a reference from one document to
another, and the vocabulary of outcomes an evaluator reports.

**Out of scope, deliberately.** Ranking, scoring, similarity, confidence, calibration, thresholds,
embeddings, storage, indexing, synchronisation, access control, and any inference of validity from
prose. Those are implementation concerns and this specification takes no position on them.

The cut is drawn so that **a conforming implementation needs no vector search, no model and no
database.** Every rule below can be evaluated with a YAML parser, a clock and a dictionary. A note
taking application can implement the whole of this specification in an afternoon.

## 3. Conformance and terminology

The key words MUST, MUST NOT, REQUIRED, SHALL, SHOULD, SHOULD NOT, RECOMMENDED, MAY and OPTIONAL
are to be interpreted as described in RFC 2119.

| Term | Meaning |
|---|---|
| **Document** | A single addressable unit of text carrying at most one frontmatter block. Typically one file. |
| **Corpus** | The set of documents an evaluator considers at once. Resolution is defined only within a corpus. |
| **Evaluator** | Software that reads validity properties and reports a verdict for a document. |
| **Valid time** | The time a statement was true in the world. Declared by the author. |
| **Transaction time** | The time a statement was recorded in the corpus. Observed by the system, never declared. |
| **Evaluation instant** | The valid time an evaluator is asked about. Usually now. |
| **Knowledge instant** | The transaction time an evaluator is asked about. Usually unset. |

Three conformance levels are defined in section 10.

## 4. Document model

A document MAY begin with a frontmatter block: a line containing exactly `---`, followed by zero or
more `key: value` lines, closed by a line containing exactly `---`.

- The block MUST be at the very start of the document. A UTF-8 byte order mark before the opening
  fence MUST be tolerated and ignored.
- An implementation MUST exclude the frontmatter block from the document body.
- An implementation MUST ignore keys it does not recognise. This vocabulary claims exactly three
  key names and no others.
- A document without a frontmatter block, or with a block declaring none of the three keys, is
  **unconstrained**: it has no declared lifetime and no declared successor. This is the normal case
  and MUST NOT be treated as an error.

`---` is also the Markdown thematic break, so an opening fence alone does not prove a block exists.
An implementation MUST NOT pair two thematic breaks and silently delete the prose between them.
The RECOMMENDED rule is to require that at least one line before the closing fence is a mapping
key. Note E in the appendix records why this matters more than it looks.

## 5. The three properties

### 5.1 `valid_from`

```yaml
valid_from: 2026-03-01
```

The date on which the document's content began to be true.

- The value MUST be an ISO 8601 calendar date in exactly the form `YYYY-MM-DD`, zero padded.
- It is interpreted as `00:00:00.000000` UTC on that date, and the bound is **inclusive**.
- A document whose `valid_from` is after the evaluation instant is **not yet valid**.

### 5.2 `valid_until`

```yaml
valid_until: 2026-09-30
```

The last date on which the document's content was true.

- The value MUST be an ISO 8601 calendar date in exactly the form `YYYY-MM-DD`, zero padded.
- It is interpreted as `23:59:59.999999` UTC on that date, and the bound is **inclusive**. A
  document valid until 2026-09-30 is valid for the whole of 30 September.
- A document whose `valid_until` is before the evaluation instant is **expired**.

Both bounds are OPTIONAL and independent. A document may declare neither, either, or both.

If both are present and `valid_from` is later than `valid_until`, the window is empty and the
document can never be valid. A conforming evaluator MUST report `invalid_metadata` in that case.
See appendix note D for a known deviation in the reference implementation.

### 5.3 `supersedes`

```yaml
supersedes: rate_limits_v1.md
```

A reference to another document in the corpus, asserting that **this document replaces that one**.

- The value is a document reference, resolved by the algorithm in section 6.
- The edge points from the referenced document to the declaring document. Reading
  `supersedes: A` in document B, the successor of A is B.
- The reference is authored. This specification defines no way to infer a supersession edge from
  prose, and an implementation MUST NOT create an edge that no document declared. Appendix note A
  records the measured cost of that decision.

A document MAY declare `supersedes` several times, or with a sequence value, if the host format
allows it. An implementation MAY support this. Support is OPTIONAL because it is not required by
the common case and adds resolution ambiguity that section 6.4 must then arbitrate.

## 6. Reference resolution

A `supersedes` value is written by a human, in a text editor, usually without checking. On a real
792 document corpus, **every** declared edge failed to resolve against a naive full path match, and
none of them failed because the target was missing. They failed because the author wrote
`[[project-notes]]` where the matcher wanted `notes/project-notes.md`.

A convention the corpus author cannot follow is a defect in the convention. Resolution is therefore
deliberately forgiving about **form** and deliberately strict about **ambiguity**.

### 6.1 Normalisation

To normalise a reference, an implementation MUST apply these steps in order:

1. Trim leading and trailing whitespace.
2. While the value is at least two characters long and begins with `[` and ends with `]`, remove
   the first and last character and trim again. This handles `[name]` and `[[name]]`, in any
   nesting.
3. If the value ends with `.md` in any letter case, remove those three characters.
4. Split on `/` and keep only the final segment.
5. Trim again.

The result is the **resolution key**.

```text
"[[notes/rate limits v1]]"   ->  "rate limits v1"
"rate_limits_v1.MD"          ->  "rate_limits_v1"
"  archive/old.md  "         ->  "old"
```

An implementation MUST apply the identical normalisation to every document in the corpus to derive
that document's own resolution key, so that a reference and a target are always compared on the
same footing.

### 6.2 Matching

A reference resolves to the document whose resolution key is equal to the reference's resolution
key. Comparison MUST be exact, after normalisation. Implementations MUST NOT apply fuzzy matching,
stemming, or nearest-string search to a reference.

A reference that matches no document in the corpus is **dangling**. A dangling reference MUST NOT
cause any document to be reported as `superseded`, and an implementation SHOULD report it to the
author. It MUST NOT be an error that prevents the document being read.

An implementation MAY retain a dangling reference internally, for example keyed on the raw text as
written, so that the claim survives if its target is later restored. Such a retained reference is
inert by the rule above.

### 6.3 Self-reference

A document that declares `supersedes` resolving to itself MUST be treated as declaring nothing. A
document cannot supersede itself, and the construction is always an authoring mistake.

### 6.4 Ambiguity

If a reference's resolution key matches **more than one** document in the corpus, the reference is
**ambiguous**.

An implementation MUST NOT guess. It MUST NOT pick the first, the newest, the nearest, or the one
in the same folder.

Every document matching an ambiguous key MUST be reported with the verdict
`ambiguous_supersession` (section 9). This fails closed: an ambiguous claim makes the target *less*
trusted, never more. The alternative, serving the target as ordinary and current because the edge
could not be resolved, is exactly the silent wrong answer this vocabulary exists to prevent.

## 7. The supersession graph

Edges form a directed graph over documents. An evaluator asks one question of it: **given a
document, what is its terminal successor, if any?**

### 7.1 Chains

Edges compose. If A is superseded by B and B is superseded by C, then the terminal successor of A
is C, and an evaluator MUST resolve the chain rather than stopping at the first step.

### 7.2 Cycles

A cycle is possible and MUST NOT cause an implementation to loop, recurse without bound, or fail.

The REQUIRED behaviour is to walk the chain recording visited documents, and to stop on the first
revisit, returning the successor reached immediately before the revisit. A cycle is an authoring
mistake; an implementation SHOULD report it, and MUST remain useful in its presence.

### 7.3 Fan-in

Two documents MAY both declare that they supersede the same target. This specification does not
require an implementation to choose between them, and an implementation MAY expose all claimants.

An implementation that must reduce to a single successor MUST document the rule it uses. Where
transaction time is available, the RECOMMENDED rule is the claim asserted **last**. See section 8.3.

## 8. Time

Two axes, independent, and conflating them is the most common implementation error.

### 8.1 Valid time

Declared by the author through `valid_from` and `valid_until`. It answers **when was this true**.
It is the axis that produces `expired` and `not_yet_valid`.

### 8.2 Transaction time

Observed by the system: the moment a document was first recorded in the corpus. It is never
declared in frontmatter, and an implementation MUST NOT accept an author's claim about it. It
answers **when did we know this**, and it is the axis that produces `not_yet_known`.

An implementation supporting transaction time MUST record the **first** write of a document and
MUST NOT overwrite it on re-indexing. Using the most recent write instead claims that a document
edited today never existed before today, which empties every replay of an earlier instant.

### 8.3 Composition, and the dating of edges

The two axes compose. Asking about valid time *June* at knowledge instant *Tuesday* means: what did
this corpus, as it stood on Tuesday, hold about the state of the world in June.

A supersession edge becomes assertable when the declaring document is written, so **an edge is
dated by the transaction time of the document that declares it.**

An implementation supporting point-in-time replay:

- MUST filter edges to those asserted at or before the knowledge instant.
- MUST apply that filter **per step** of a chain, not to the terminal successor. In a chain
  A to B to C where only the first edge predates the instant, the answer is B. Filtering only the
  terminal answer would return C, a document that had not yet superseded anything.
- MUST apply an edge whose assertion time is unknown. An undated edge applying unconditionally
  fails closed; ignoring it would serve a memory the corpus explicitly marks as stale.
- MUST leave visible a document whose own transaction time is unknown. Hiding it would fail closed
  in the wrong direction, silently emptying results for corpora that predate the record.

Those last two rules point in opposite directions on purpose. An unknown *edge* date suppresses a
document; an unknown *document* date does not. In both cases the choice is the one that cannot
produce a confident stale answer.

## 9. Evaluation

An evaluator takes a document, the corpus's supersession graph, an evaluation instant, and
optionally a knowledge instant. It returns exactly one **verdict**.

### 9.1 Verdict vocabulary

| Verdict | Meaning |
|---|---|
| `ok` | The document declares nothing that disqualifies it at these instants. |
| `invalid_metadata` | A validity property is present but unparseable, or the declared window is empty. |
| `not_yet_known` | The document had not been recorded at the knowledge instant. |
| `ambiguous_supersession` | A supersession reference resolves to this document and to at least one other. |
| `superseded` | Another document declares that it replaces this one. The successor MUST be reported alongside the verdict. |
| `expired` | The evaluation instant is after `valid_until`. |
| `not_yet_valid` | The evaluation instant is before `valid_from`. |

Seven verdicts, all derivable from declared metadata and two clocks. No verdict in this
specification depends on a score, a model, or a similarity measure.

An implementation MAY define additional verdicts for concerns outside this specification, such as
low confidence or unverified entailment. Such verdicts MUST be namespaced or documented as
extensions, and MUST NOT reuse a name defined above with different meaning.

### 9.2 Precedence

Exactly one verdict is reported. Where several apply, the first match in this order MUST win:

```text
1. invalid_metadata
2. not_yet_known
3. ambiguous_supersession
4. superseded
5. expired  |  not_yet_valid     (mutually exclusive)
6. ok
```

The ordering is not arbitrary and two positions carry real weight.

**`not_yet_known` outranks `superseded`** because a document that did not exist at the knowledge
instant cannot meaningfully have a fate. Reporting `superseded` there would describe what later
happened to a document the caller is not allowed to see.

**`invalid_metadata` outranks everything** because an unparseable window is a document making a
claim nobody can check. It fails closed as a single document rather than as a crash, so one
malformed document MUST NOT prevent evaluation of the rest of the corpus.

### 9.3 Algorithm

```text
evaluate(document, graph, at_valid_time, at_knowledge_time):

    try:
        from, until = parse_bounds(document)
    except ParseError:
        return invalid_metadata
    if from and until and from > until:
        return invalid_metadata

    if at_knowledge_time is not None:
        first_seen = transaction_time_of(document)      # first write, or unknown
        if first_seen is not None and first_seen > at_knowledge_time:
            return not_yet_known

    if resolution_key(document) is ambiguous in graph:
        return ambiguous_supersession

    successor = terminal_successor(document, graph, at_knowledge_time)
    if successor is not None:
        return superseded with successor

    if until is not None and at_valid_time > until:
        return expired
    if from is not None and at_valid_time < from:
        return not_yet_valid

    return ok
```

An evaluation instant given without a timezone MUST be interpreted as UTC.

### 9.4 What an evaluator does with a verdict

Nothing is mandated. This specification defines what is true about a document, not what an
application should do about it.

Two behaviours are RECOMMENDED because they are the point of the exercise:

- A `superseded` document SHOULD be presented together with its successor, and the successor
  SHOULD be ordered above it, regardless of any other ranking signal.
- A document that is `superseded`, `expired`, `not_yet_valid`, `not_yet_known`,
  `ambiguous_supersession` or `invalid_metadata` SHOULD NOT be presented to a language model as
  current fact without its verdict attached.

## 10. Conformance levels

An implementation SHOULD state which level it implements.

**Level 1, Reader.** Parses the frontmatter block, reads the three keys, ignores unknown keys,
excludes the block from the body, and exposes the values. Applies section 6 normalisation. Does not
evaluate.

**Level 2, Evaluator.** Level 1, plus the supersession graph of section 7 and the verdict algorithm
of section 9 at a single evaluation instant. Reports all seven verdicts. This is the level a note
taking application or plugin should target.

**Level 3, Bi-temporal evaluator.** Level 2, plus transaction time, `not_yet_known`, and
point-in-time replay with per-step edge filtering as specified in section 8.3.

A Level 2 implementation MUST NOT report `not_yet_known`, since it has no transaction time axis to
derive it from.

## 11. Test vectors

A corpus of four documents. Transaction times are given for Level 3 only.

```yaml
# a.md    (first recorded 2026-01-10)
---
valid_until: 2026-06-30
---

# b.md    (first recorded 2026-07-01)
---
supersedes: [[a]]
valid_from: 2026-07-01
---

# c.md    (first recorded 2026-08-01)
---
supersedes: b.md
---

# d.md    (first recorded 2026-01-01)
---
valid_from: 2026-12-01
valid_until: 2026-11-01
---
```

| # | Document | Evaluation instant | Knowledge instant | Expected verdict | Notes |
|---|---|---|---|---|---|
| 1 | `a.md` | 2026-08-19 | unset | `superseded` by `c.md` | Chain a to b to c resolves to the terminal successor. |
| 2 | `b.md` | 2026-08-19 | unset | `superseded` by `c.md` | |
| 3 | `c.md` | 2026-08-19 | unset | `ok` | |
| 4 | `d.md` | 2026-08-19 | unset | `invalid_metadata` | Empty window: `valid_from` is after `valid_until`. |
| 5 | `a.md` | 2026-08-19 | 2026-07-15 | `superseded` by `b.md` | Per step. The b to c edge is not yet asserted. |
| 6 | `c.md` | 2026-08-19 | 2026-07-15 | `not_yet_known` | Recorded after the knowledge instant. |
| 7 | `a.md` | 2026-08-19 | 2026-01-05 | `not_yet_known` | Outranks any consideration of its window. |
| 8 | `a.md` | 2026-05-01 | 2026-06-01 | `ok` | Inside its window, and no edge asserted yet. |
| 9 | `a.md` | 2026-08-19 | 2026-06-01 | `expired` | Known, past `valid_until`, not yet superseded. |

Two further vectors, over a separate corpus:

```yaml
# notes/policy.md   and   archive/policy.md   both exist
# update.md
---
supersedes: policy
---
```

| # | Document | Expected verdict | Notes |
|---|---|---|---|
| 10 | `notes/policy.md` | `ambiguous_supersession` | Two documents share the resolution key `policy`. |
| 11 | `archive/policy.md` | `ambiguous_supersession` | Both targets are marked, neither is guessed at. |

An implementation claiming conformance SHOULD pass every vector at its level. Vectors 5 to 9
require Level 3.

## 12. Extension

Unknown keys MUST be ignored, so any host application may put anything else in the same
frontmatter block. This vocabulary coexists with Obsidian Properties, Jekyll front matter, Hugo
front matter, Dataview fields and Bases properties without collision, because it claims three names
and no more.

An implementation adding validity concepts beyond this specification SHOULD prefix its keys, for
example `x_myapp_reviewed_by`. Future versions of this specification will not claim any key
beginning `x_`.

---

## 13. Non-goals

Stated so that nobody has to guess, and so that a future version cannot quietly acquire them.

- **Inferring validity from prose.** Out of scope, permanently. See appendix note A.
- **Confidence, thresholds and calibration.** An engine concern.
- **Ranking and similarity.** An engine concern.
- **Entailment.** Whether a document actually answers a question is a different problem.
- **Access control.** Validity is not permission.
- **Sub-document validity.** Version 1.0 declares validity of a whole document only. Per-section
  validity is a plausible version 2 and is not specified here.
- **Timezones.** Version 1.0 is date only and UTC only. See appendix note C.

## 14. Appendix: design notes

These are not normative. They record why the rules are what they are, including where the answer is
uncomfortable.

### Note A: authored edges have terrible coverage, and that is the honest trade

This vocabulary requires a human to write `supersedes:`. That is the whole design, and its cost is
measured rather than assumed. On the reference implementation's own 792 document corpus:

- **2 documents** declared `supersedes:`.
- **60 documents** closed a decision only in prose.
- An automated linter, reviewing those 60, could safely declare **zero** of them.

Narrating a change is not declaring one. Part is not whole. Augmenting is not replacing. Those
distinctions are invisible to a pattern and obvious to the author.

A model would do better than a linter. It would not do *reliably* better, and the premise here is
that a confidently wrong supersession edge is worse than a missing one: a wrong edge suppresses a
true document and promotes a false one, with the full weight of an explicit declaration behind it.

So the honest claim is a trade, not a win. **This vocabulary buys precision on the edges it has and
pays for it in coverage.** An implementation that layers inference on top is doing something this
specification neither forbids nor endorses, and it MUST NOT present an inferred edge as a declared
one.

### Note B: why resolution is forgiving about form and strict about ambiguity

These are the same decision seen twice. A reference is authored by hand, so the failure mode that
actually occurs is a well-formed reference written in an unexpected style, not a reference to
something absent. Forgiving normalisation removes that failure mode entirely.

Ambiguity is the opposite case: the corpus genuinely does not determine an answer. Guessing there
would produce a confident wrong result, which is the one outcome the vocabulary exists to prevent.
Hence: guess at style, never at target.

### Note C: why dates and not timestamps

`valid_until: 2026-09-30` is something a human will write. `valid_until: 2026-09-30T23:59:59+02:00`
is not, and a property nobody fills in has no coverage and therefore no value.

The cost is real and is accepted: a document whose validity genuinely ends at a particular hour
cannot say so, and an author in UTC+13 will find the boundary lands on the wrong side of their
midnight. A future version may add an optional timestamp form. Version 1.0 chooses the property
people will actually write.

### Note D: known deviation in the reference implementation

RE-call 0.9.5 does not detect the empty window of section 5.2. Given `valid_from` later than
`valid_until`, it reports `expired` or `not_yet_valid` rather than `invalid_metadata`. The document
still fails closed, since no instant can satisfy an empty window, but the reported reason is
misleading. Test vector 4 covers it. This specification states the intended behaviour; the
implementation is expected to follow.

### Note E: `---` is also a horizontal rule

An opening `---` does not prove a frontmatter block exists, because a document may simply begin
with a thematic break. Pairing it with the next `---` in the file deletes everything between two
unrelated rules, with no signal to the reader and no error.

The asymmetry decides the rule. Wrongly *pairing* a block loses body text. Wrongly *refusing* one
loses the validity metadata **and** dumps the raw frontmatter into the body as prose. Both are bad,
so recognition should be permissive about what counts as a member line while requiring at least one
actual mapping key before the closing fence.

## 15. Prior art

Bi-temporal modelling is old and well understood in databases; SQL:2011 standardised system time
and application time, and this vocabulary is a minimal text-file expression of the same two axes.
What is unusual here is not the temporality, it is that **supersession is declared by the author in
the document rather than inferred by a system at ingestion**.

Systems that infer instead: [Graphiti](https://github.com/getzep/graphiti) invalidates contradicted
facts using a model call per episode; [Mem0](https://github.com/mem0ai/mem0) accumulates and
reasons about time at retrieval. Both achieve coverage this vocabulary cannot. Both accept a class
of confidently wrong edge this vocabulary refuses to create. Neither approach is strictly better
and the trade should be made deliberately.
